\section{Phase 3: OS Fingerprinting Engine \& Multi-Platform Empirical Signatures}\label{sec:fp}

The operating-system fingerprinting engine classifies target hosts across multiple protocol layers.
Instead of matching single-packet signatures against static tables, the engine scores candidate OS families
using passive packet observations, active RFC probes, sequence tracking, and service banner hints.

\subsection{Probabilistic Weighted Scoring \& Calibration Architecture}
Every incoming packet attribute is evaluated by an independent strategy module~$k$. Each strategy
assigns evidence weights $w_{k,c}$ to four target operating system candidate families:
\begin{center}
$c \;\in\; \mathcal{C} \;=\; \{\text{Windows}, \ \text{Linux}, \ \text{macOS / BSD}, \ \text{Network Device}\}$
\end{center}

\subsubsection{Mathematical Scoring Formulation}
The cumulative raw score $S(c)$ for each candidate operating system family is calculated by summing the
evidence weights contributed across all active strategies:
\begin{equation}
S(c) \;=\; \sum_{k=1}^{M} w_{k,c}(\text{Observed Feature}_k)
\label{eq:score}
\end{equation}
where $M$ denotes the total number of evaluated feature vectors. The raw score is normalized into an
initial probability distribution $P(c)$ across all candidate classes:
\begin{equation}
P(c) \;=\; \frac{\max(0, \, S(c))}{\sum_{c' \in \mathcal{C}} \max(0, \, S(c'))} \times 100\%
\label{eq:prob}
\end{equation}

\subsubsection{Low-Evidence Damping \& Score Calibration}
To avoid overstating confidence when few features match, the engine dampens the score when total evidence
is sparse. If an uncalibrated formula evaluated a single weak feature, it could report 100\% confidence on
scant data. To prevent this, the engine runs a four-stage calibration pipeline:
\begin{enumerate}
    \item \textbf{Low-Evidence Damping:} If the total accumulated evidence score falls below the minimum
    reliability threshold $\theta_{\text{damp}} = 4.0$, the winning percentage is damped proportionally:
    \begin{equation}
    \text{Confidence}(c) \;=\; \begin{cases}
    P(c) \cdot \left(\dfrac{\sum_{c'} S(c')}{\theta_{\text{damp}}}\right), & \text{if } \sum_{c'} S(c') < \theta_{\text{damp}} = 4.0\\[8pt]
    P(c), & \text{otherwise}
    \end{cases}
    \label{eq:damping}
    \end{equation}
    \item \textbf{Tie-Detection Alert:} When the separation between the top two candidates is marginal
    ($|P(c_{\text{1st}}) - P(c_{\text{2nd}})| \le 8\%$), the engine appends a low-certainty alert to the evidence trail.
    \item \textbf{Uncertainty Qualifier:} If the winning confidence satisfies $\text{Confidence} < 40\%$,
    the reported OS family is tagged with an explicit \textsf{"(uncertain)"} disclaimer.
    \item \textbf{Zero-Evidence Fallback:} If $\sum_{c'} S(c') \le 0$ (no features match), the engine
    returns \textsf{"Unknown"} with a baseline confidence of 20\%.
\end{enumerate}

\subsection{The Seven Core Fingerprinting Strategies: Theory, Numbering \& Rules}
Our engine implements seven distinct diagnostic strategies combining passive packet inspection and
active differential probing:

\subsubsection{Strategy 1: Initial TTL Normalization \& Router Hop Recovery}
\textbf{Protocol Basis (RFC 791):} Every operating system kernel initializes outbound IPv4 datagrams
with a fixed default Time to Live (TTL). As the packet traverses router hops, intermediate gateways
decrement the field by~1. Because TTL can only decrease, the scanner executes a \textbf{round-up
normalization function} mapping the observed value $\text{TTL}_{\text{obs}}$ to the nearest standard baseline:
\begin{equation}
\text{Initial TTL} \;=\; \min \{ T \in \{32, \, 64, \, 128, \, 255\} \mid T \ge \text{TTL}_{\text{obs}} \}
\end{equation}
The transit hop count is directly deduced as:
\begin{equation}
\text{Router Hops } (H) \;=\; \text{Initial TTL} - \text{TTL}_{\text{obs}}
\end{equation}

\textbf{Evidence Weight Allocations:}
\begin{itemize}
    \item $\text{Initial TTL} = 128 \implies \text{Windows family } (w = +4.0 \text{ for SYN/ACK}, \ w = +4.5 \text{ for RST})$.
    \item $\text{Initial TTL} = 64 \implies \text{Linux } (w = +2.0) \text{ and } \text{macOS/BSD } (w = +2.0)$.
    \item $\text{Initial TTL} = 255 \implies \text{Network Device / Appliance } (w = +3.0 \text{ SYN/ACK}, \ w = +4.0 \text{ RST})$.
    \item $\text{Initial TTL} = 32 \implies \text{Legacy Windows 9x-era stack } (w = +1.0)$.
\end{itemize}

\subsubsection{Strategy 2: Multi-Sample IP-ID Sequence Classification}
\textbf{Protocol Basis (RFC 6864):} Rather than evaluating a single static IP-ID integer, the engine
transmits a sequence of probes over time, extracts the sequence of IPv4 Identification values
$\{\mathrm{ID}_0, \mathrm{ID}_1, \ldots, \mathrm{ID}_n\}$, and computes consecutive 16-bit modular deltas:
\begin{equation}
\Delta_i \;=\; (\mathrm{ID}_i - \mathrm{ID}_{i-1}) \bmod 65536
\end{equation}
The engine categorizes the generation pattern into five concrete mathematical archetypes:
\begin{enumerate}
    \item \texttt{ALL\_ZERO} ($\forall i: \mathrm{ID}_i = 0$, $\text{DF}=1$): RFC~6864 atomic datagram $\implies$ Modern Linux Kernel ($w = +2.5$).
    \item \texttt{STRICT\_INCREMENTAL} ($1 \le \Delta_i \le 10$): Sequential global counter $\implies$ Windows 10/11 stack ($w = +2.5$).
    \item \texttt{BROKEN\_INCREMENTAL} ($11 \le \Delta_i \le 1000$): Global counter under traffic load $\implies$ Windows host ($w = +2.0$).
    \item \texttt{CONSTANT\_NONZERO} ($\forall i: \mathrm{ID}_i = K \ne 0$): Static counter $\implies$ Network Appliance ($w = +2.5$).
    \item \texttt{RANDOM\_POSITIVE} ($\Delta_i > 1000$): Cryptographic PRNG counter $\implies$ Darwin / BSD ($w = +1.5$).
\end{enumerate}

\subsubsection{Strategy 3: TCP Timestamp Clock Frequency (\texorpdfstring{$R$}{R}) \& Uptime Recovery}
\textbf{Protocol Basis (RFC 7323):} The TCP Timestamp option contains a 32-bit timestamp value
(\texttt{TSval}) that increments at a fixed kernel clock frequency. By sampling timestamps
$(\mathrm{TSval}_1, t_1)$ and $(\mathrm{TSval}_2, t_2)$ separated by elapsed physical time $\Delta t$,
the engine recovers the operating system's internal timer rate $R$:
\begin{equation}
R \;=\; \frac{(\mathrm{TSval}_2 - \mathrm{TSval}_1) \bmod 2^{32}}{t_2 - t_1} \ \text{Hz}
\end{equation}
The frequency is matched against known kernel timer categories:
\begin{itemize}
    \item $R \approx 1000 \ \text{Hz} \ (700\text{--}1400 \ \text{Hz}):$ 1\,ms tick $\implies$ Windows 10/11 ($w = +2.0$) or Linux low-latency ($w = +1.0$).
    \item $R \approx 250 \ \text{Hz} \ (180\text{--}350 \ \text{Hz}):$ Standard Linux kernel (\texttt{CONFIG\_HZ=250}) $\implies$ Linux ($w = +2.5$).
    \item $R \approx 100 \ \text{Hz} \ (70\text{--}150 \ \text{Hz}):$ Traditional Unix/Linux or older Windows $\implies$ Linux ($w = +1.5$), Windows ($w = +1.0$).
    \item $R \approx 10 \ \text{Hz} \ (5\text{--}25 \ \text{Hz}):$ Legacy Windows tick counter $\implies$ Windows ($w = +2.0$).
    \item Randomized Offset ($\Delta\mathrm{TSval} > 10^7$): RFC~7323 PRNG protection $\implies$ Apple macOS / iOS ($w = +2.5$).
\end{itemize}
When $R$ is stable, the host uptime is estimated and presented to the operator:
\begin{equation}
\text{Estimated Host Uptime (seconds)} \;=\; \frac{\mathrm{TSval}_{\text{latest}}}{R}
\end{equation}

\subsubsection{Strategy 4: Active RFC 3168 Explicit Congestion Notification (ECN) Probing}
\textbf{Protocol Basis (RFC 3168):} The scanner dispatches an active probe segment with both ECN-Echo (ECE)
and Congestion Window Reduced (CWR) flags asserted ($\text{Flags} = \mathtt{0xC2}$). Under standard RFC~3168
negotiation, an ECN-aware server echoes ECE while clearing CWR in its SYN/ACK:
\begin{itemize}
    \item \texttt{ECN\_SUPPORTED} ($\text{Flags} = \mathtt{0x52}$, ECE set, CWR clear): Full RFC compliance $\implies$ Linux / Darwin ($w = +2.0$ each).
    \item \texttt{ECN\_IGNORED} ($\text{Flags} = \mathtt{0x12}$, ECE/CWR clear): Flags ignored $\implies$ Default Windows Stack ($w = +2.0$).
    \item \texttt{ECN\_REJECTED\_RST} (RST returned on probe): Target drops on reserved flags $\implies$ Network Appliance ($w = +1.5$).
    \item \texttt{ECN\_DROPPED} (Probe timeout expiration): Middlebox silently drops probe $\implies$ Strict Firewall ($w = +2.0$).
\end{itemize}

\subsubsection{Strategy 5: Ambiguous TCP Flag Handling (The RFC 793 ``Rule-Breaker'' Probe) }
\textbf{Protocol Basis (RFC 793 / RFC 9293):} To test RFC conformity, the engine transmits invalid flag
combinations ($\text{SYN}+\text{FIN} = \mathtt{0x03}$, NULL $= \mathtt{0x00}$, or XMAS $= \mathtt{0x29}$)
toward open and closed ports. RFC~793 dictates that packets lacking an ACK bit arriving on an open port
must be silently discarded:
\begin{itemize}
    \item \textbf{Windows Stack Non-Compliance:} Violates RFC~793 by returning a TCP RST/ACK response
    ($\text{Flags} = \mathtt{0x14}$) on open ports $\implies \text{Windows } (w = +2.5)$.
    \item \textbf{Linux RFC Compliance:} Conforms to RFC~793 by silently dropping the illegal probe on open
    ports while emitting RST on closed ports $\implies \text{Linux } (w = +2.0), \text{ macOS/BSD } (w = +1.0)$.
    \item \textbf{Darwin / BSD Filtering:} Silently drops invalid probes across open and closed ports
    $\implies \text{Darwin / BSD } (w = +2.5)$.
\end{itemize}

\subsubsection{Strategy 6: Autonomous ICMP / UDP Diagnostic Battery }
\textbf{Protocol Basis (RFC 792):} When TCP ports are comprehensively firewalled, the engine shifts to Layer~3
and Layer~4 auxiliary protocols:
\begin{itemize}
    \item \textbf{ICMP Code 9 Reflection:} The scanner transmits an ICMP Echo Request with an illegal code
    ($\text{Type} = 8, \text{Code} = 9$). Windows normalizes the field to standard $\text{Code} = 0$
    ($w_{\text{Windows}} = +3.0$), whereas Linux and Darwin verbatim reflect $\text{Code} = 9$ ($w = +2.0$).
    \item \textbf{ICMP DF Bit Behavior:} In response to ICMP Echo requests, Apple Darwin sets the
    Don't-Fragment bit ($\text{DF}=1$) in accordance with RFC~6864 ($w_{\text{macOS}} = +3.0$); Windows and Linux clear it.
    \item \textbf{UDP Port Unreachable Payload Quoting ($U_1$):} Transmitting a UDP datagram to a closed high
    port triggers an ICMP Port Unreachable message ($\text{Type} = 3, \text{Code} = 3$). Darwin strictly quotes
    the minimum 28 octets (IPv4 header + 8 bytes UDP) ($w_{\text{macOS}} = +2.5$), whereas Windows quotes extensive
    payload segments ($> 28$ bytes, typically up to 328 bytes) ($w_{\text{Windows}} = +2.5$).
\end{itemize}

\subsubsection{Strategy 7: Cross-Layer Application Banner Correlation \& Header Order }
\textbf{Protocol Basis (RFC 7230 / Cross-Layer Fusion):} Application-layer service banners provide
authoritative, declarative evidence that is fused into the Layer~3/4 network stack scoring matrix:
\begin{itemize}
    \item \textbf{Declarative Daemon Signatures:} Regex patterns matching service banners contribute high-confidence evidence ($w = +3.0 \text{ to } +4.5$):
    \begin{itemize}
        \item Windows: \texttt{Microsoft-IIS}, \texttt{Microsoft FTP}, \texttt{OpenSSH\_for\_Windows}, \texttt{Win32/Win64}.
        \item Linux: \texttt{Ubuntu}, \texttt{Debian}, \texttt{CentOS}, \texttt{vsftpd}, \texttt{dropbear}.
        \item macOS/BSD: \texttt{Darwin}, \texttt{FreeBSD}, \texttt{OpenBSD}, \texttt{NetBSD}.
        \item Network Device: \texttt{Cisco}, \texttt{MikroTik}, \texttt{OpenWrt}, \texttt{Fortinet}, \texttt{Juniper}.
    \end{itemize}
    \item \textbf{RFC 7230 HTTP Header Sequencing:} Evaluates whether the \texttt{Server:} header line
    precedes or follows the \texttt{Date:} header in web server responses ($w = +0.5$).
    \item \textbf{Closed-Port RST Tier Ingestion:} Overcomes the primary limitation of closed-port scanning:
    when an open port is absent, any cached banner signature injects an authoritative tier hint directly
    into the version refinement engine.
\end{itemize}

\subsubsection{TCP Option Order \& Advertised Window Signatures}
\textbf{Option Ordering Sequence (Excluding NOP/EOL Padding):} Because TCP option layouts are set
during kernel compilation, they provide a reliable passive signal ($w = +3.0$):
\begin{itemize}
    \item Windows 10/11: \texttt{['MSS', 'WSCALE', 'SACK\_PERMITTED']}\\
    or \texttt{['MSS', 'WSCALE', 'SACK\_PERMITTED', 'TIMESTAMP']}
    \item Modern Linux: \texttt{['MSS', 'SACK\_PERMITTED', 'TIMESTAMP', 'WSCALE']}
    \item Apple macOS / Darwin: \texttt{['MSS', 'WSCALE', 'TIMESTAMP', 'SACK\_PERMITTED']}
\end{itemize}
\textbf{Advertised Window Signatures:} Observed receive windows are evaluated against known profiles:
\begin{itemize}
    \item Windows: $\{8192, \ 16384, \ 64240, \ 65535\}$
    \item Linux: $\{5840, \ 14600, \ 29200, \ 64240, \ 65160, \ 65535\}$
    \item Darwin / BSD: $\{65535, \ 33304, \ 33456\}$
\end{itemize}
Overlap is deliberately supported ($w = +1.5$) as supporting evidence.

or Windows 7/8''}) rather than asserting unsupportable certainty.
